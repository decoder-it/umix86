==============================================================================
 UMIX/86 - CALLING THE CHAT API FROM A WEB PAGE
 Build: V0R138   API: X-API-Version 13
==============================================================================

This file shows how to drive the UMIX/86 chat room from a browser: claim a
nickname, send text, poll the shared history, list users, and leave.  The same
room is used by people typing CHAT at the guest's USERID: prompt, so browser
and serial users see each other's messages.


------------------------------------------------------------------------------
 1. PREREQUISITES
------------------------------------------------------------------------------

Guest:
  * MUX ON in STARTUP.JCL (the default test image does this).
  * SLIP and TCP OFF.  The chat history lives in the 0x2900 window, which
    TCP.SYS also uses; the chat endpoints return 503 while SLIP/TCP is on.
  * API.SYS loaded (the STARTUP.JCL "API ROUTE ..." lines do this).

Host:
  * serial_mux.py with an HTTP listener, e.g.

      python3 tools/serial_mux.py --serial unix:/tmp/umix-ser.sock \
          --listen 127.0.0.1:2323 --http-listen 127.0.0.1:8080

  * Load the page one of three ways:

      A) From the guest (no browser flags):
         put the HTML on C: as INDEX.HTM and open http://127.0.0.1:8080/
         (guest static page limit: 4000 bytes).  The page then uses relative
         /api paths.

      B) From a LOCAL file (recommended for development, no CORS changes):
         the guest sends no CORS headers, and the browser still enforces
         same-origin, so launch Chrome/Chromium with web security disabled:

           chromium --disable-web-security \
               --user-data-dir=/tmp/umix-chat \
               file:///path/to/chatpage.html

         The page detects file:// and calls http://127.0.0.1:8080 (edit the
         API constant if your --http-listen host/port differs).  Always pair
         --disable-web-security with a throwaway --user-data-dir.
         Firefox's security.fileuri.strict_origin_policy=false is not enough
         for fetch() in recent versions; use Chromium or option C.

      C) Same-origin proxy (any browser, no flags):
         run the tiny proxy in section 6, which serves the page and forwards
         /api/* to the bridge.  Open http://127.0.0.1:8000/; the page then uses
         relative /api paths.

  * The guest HTTP parser and the bridge's web session are serialized.  Do not
    fire parallel fetches: queue calls (the example below does).


------------------------------------------------------------------------------
 2. ENDPOINTS
------------------------------------------------------------------------------

  POST   /api/chat/join       {"nick":"ALICE"}            -> {"token":1}
  POST   /api/chat/send       {"token":1,"text":"hi"}     -> {"seq":4}     202
  GET    /api/chat/messages                               -> all retained
  GET    /api/chat/messages/3                             -> seq > 3
  GET    /api/chat            -> {"count","nicks","api","latest"}
  DELETE /api/chat/join/1     -> {"ok":true}

Rules:
  * nickname: 2..9 characters, A-Z / 0-9 (letters are upcased), not SYSOP
  * text: up to 50 characters; control characters and double quotes are
    stripped, backslash becomes '/'
  * history: the last 16 lines, each with a 16-bit sequence number
  * token: use the value returned by join on send/messages; tokens are lost on
    reboot, SYS reload, TCP ON, or when the guest image is rebuilt

Response bodies are JSON.  Errors are {"error":"..."} with:
  400 bad request / bad nick / bad token     409 nickname already in use
  503 chat unavailable (MUX off or SLIP/TCP on)

Every reply has "Connection: close"; each fetch is a new connection.

Sequence numbers: GET /api/chat/messages/<N> returns only records with
seq > N.  Remember the "latest" value (or the last seq you printed) and pass
it back next time.  If you pass an N older than the oldest retained line you
simply get the retained history.  The counter is 16-bit and wraps at 65535.


------------------------------------------------------------------------------
 3. QUICK TEST WITH CURL
------------------------------------------------------------------------------

  # claim a nickname; note the token
  curl -s -X POST -d '{"nick":"alice"}' http://HOST/api/chat/join
  # -> {"token":1}

  # send a line (202 Accepted)
  curl -s -X POST -d '{"token":1,"text":"hello from curl"}' \
       http://HOST/api/chat/send
  # -> {"seq":1}

  # read everything retained
  curl -s http://HOST/api/chat/messages
  # -> {"latest":1,"messages":[{"seq":1,"text":"ALICE: hello from curl"}]}

  # read only what is newer than sequence 1
  curl -s http://HOST/api/chat/messages/1
  # -> {"latest":1,"messages":[]}

  # who is here (terminal nicks + API nicks)
  curl -s http://HOST/api/chat

  # leave
  curl -s -X DELETE http://HOST/api/chat/join/1
  # -> {"ok":true}


------------------------------------------------------------------------------
 4. JAVASCRIPT THAT WORKS WITH THIS GUEST
------------------------------------------------------------------------------

Three rules make the difference:

  1. Serialize every request.  Keep one promise chain and append each call to
     it.  Parallel fetches confuse the guest's single global HTTP parser.

  2. Expect "Connection: close".  Do not use keep-alive; a plain fetch() is
     fine, but do not pipeline requests.

  3. Poll with the last sequence number you saw.  Do not poll faster than
     about once per 2 seconds; the serial link is paced and the bridge locks
     web sessions.

Minimal helper:

  let chain = Promise.resolve();
  function serial(fn) { chain = chain.then(fn, fn); return chain; }

  const API = location.protocol === 'file:' ? 'http://127.0.0.1:8080' : '';
  async function api(method, path, body) {
    const r = await fetch(API + path, {
      method,
      headers: body ? {'Content-Type': 'application/json'} : {},
      body: body ? JSON.stringify(body) : null
    });
    const text = await r.text();
    let data;
    try { data = JSON.parse(text); } catch (e) { data = {error: text}; }
    if (!r.ok) {
      const err = new Error(data.error || ('HTTP ' + r.status));
      err.status = r.status;
      throw err;
    }
    return data;
  }

 5. COMPLETE SELF-CONTAINED PAGE (about 2.4 KB, fits the 4000-byte limit)
------------------------------------------------------------------------------

Ready-made files in this repository:
  chat_local.htm    open locally (absolute API base, full UI, no size limit)
  chat_umix.htm     upload as INDEX.HTM or build it in with
                    UMIX_INDEX=chat_umix.htm python3 tools/mkfat.py
                    (2,960 bytes, relative /api paths)
The listing below is the same design in compact form.

Save this as chatpage.html.  Either open it directly with the Chromium
command from section 1B, or upload it as INDEX.HTM and open http://HOST/.
The API constant at the top of the script switches between the two: relative
paths when served by the guest, http://127.0.0.1:8080 for file://.

------------------------------------------------------------------------------
<!doctype html><meta charset=utf-8><title>UMIX chat</title>
<style>
body{font:14px monospace;background:#111;color:#ddd;margin:12px}
input,button{font:inherit;background:#1b1b1b;color:#ddd;border:1px solid #444}
#log{height:260px;overflow:auto;border:1px solid #444;padding:4px;white-space:pre-wrap}
</style>
<h3>UMIX/86 chat</h3>
<div id=j><input id=nick size=9 placeholder=nick maxlength=9>
<button onclick="join()">join</button></div>
<div id=s style="display:none"><input id=msg size=50 maxlength=50>
<button onclick="send()">send</button><button onclick="leave()">leave</button></div>
<div id=users></div><div id=log></div>
<script>
const API=location.protocol==='file:'?'http://127.0.0.1:8080':'';
let tok=null,since=0,chain=Promise.resolve(),ticks=0;
function serial(f){chain=chain.then(f,f);return chain}
async function api(m,p,b){
  let r=await fetch(API+p,{method:m,headers:b?{'Content-Type':'application/json'}:{},
    body:b?JSON.stringify(b):null});
  let t=await r.text(),j;try{j=JSON.parse(t)}catch(e){j={error:t}}
  if(!r.ok){let e=new Error(j.error||('HTTP '+r.status));e.status=r.status;throw e}
  return j}
function log(x){let d=document.getElementById('log');d.textContent+=x+'\n';d.scrollTop=d.scrollHeight}
function bad(e){log('! '+e.message)}
function join(){serial(async()=>{try{
  let j=await api('POST','/api/chat/join',{nick:document.getElementById('nick').value});
  tok=j.token;since=0;
  document.getElementById('j').style.display='none';
  document.getElementById('s').style.display='';
  log('joined');}catch(e){bad(e)}})}
function send(){serial(async()=>{
  let m=document.getElementById('msg');if(!m.value)return;try{
  await api('POST','/api/chat/send',{token:tok,text:m.value});m.value='';
  }catch(e){bad(e)}})}
function leave(){serial(async()=>{try{await api('DELETE','/api/chat/join/'+tok)}catch(e){}
  tok=null;document.getElementById('s').style.display='none';
  document.getElementById('j').style.display='';log('left')})}
async function tick(){
  if(!tok||document.hidden)return;
  try{
    let m=await api('GET','/api/chat/messages/'+since);
    for(let x of m.messages)log(x.seq+': '+x.text);
    since=m.latest;
    if((ticks++%3)===0){
      let u=await api('GET','/api/chat');
      document.getElementById('users').textContent=
        'users: '+u.nicks.concat(u.api).join(' ');
    }
  }catch(e){bad(e)}
}
setInterval(()=>serial(tick),2000);
</script>

 6. RUNNING FROM A LOCAL FILE, OR THROUGH A SAME-ORIGIN PROXY
------------------------------------------------------------------------------

Option B (local file, Chromium with web security off):

  chromium --disable-web-security --user-data-dir=/tmp/umix-chat \
      file:///home/you/chatpage.html

  The page sees location.protocol == 'file:' and uses
  http://127.0.0.1:8080 as its API base.  Change that constant at the top of
  the script if your --http-listen port is different.  This is the quickest
  development loop: edit the file, reload the tab.

Option C (any browser, no flags): save the page as chatpage.html next to the
script below, run it, and open http://127.0.0.1:8000/ .  It serves the page and
forwards /api/* to the bridge, so the browser sees one origin and no CORS or
web-security flag is involved.

  python3 - <<'PY'
  import http.server, socketserver, urllib.request, urllib.error
  UP = 'http://127.0.0.1:8080'
  PAGE = 'chatpage.html'
  class H(http.server.BaseHTTPRequestHandler):
      def _proxy(self):
          n = int(self.headers.get('Content-Length', '0') or 0)
          data = self.rfile.read(n) if n else None
          req = urllib.request.Request(UP + self.path, data=data,
              method=self.command,
              headers={'Content-Type': self.headers.get('Content-Type', 'application/json')})
          try: r = urllib.request.urlopen(req, timeout=30)
          except urllib.error.HTTPError as e: r = e
          b = r.read(); self.send_response(r.status)
          self.send_header('Content-Type', 'application/json')
          self.send_header('Content-Length', str(len(b)))
          self.end_headers(); self.wfile.write(b)
      def do_GET(self):
          if self.path.startswith('/api/'): return self._proxy()
          b = open(PAGE, 'rb').read()
          self.send_response(200); self.send_header('Content-Type', 'text/html')
          self.send_header('Content-Length', str(len(b)))
          self.end_headers(); self.wfile.write(b)
      do_POST = do_DELETE = _proxy
      def log_message(self, *a): pass
  socketserver.TCPServer(('127.0.0.1', 8000), H).serve_forever()
  PY

  Because the page is now served over http, its API constant evaluates to ''
  (relative paths), so /api/chat/* goes to the proxy and then to the guest.

Firefox: file:// pages are blocked from fetching http even with
security.fileuri.strict_origin_policy=false in current releases.  Use
Chromium option B or the proxy in option C.

Do not enable CORS on the guest just for this.  Option B changes one browser
flag; option C keeps a single origin.  Neither needs a kernel/overlay change.


------------------------------------------------------------------------------
 7. NOTES, LIMITS AND COMMON MISTAKES
------------------------------------------------------------------------------

  * 503 "chat unavailable": either the console ran `CHAT OFF`, or SLIP/TCP is
    on.  Run `CHAT ON` / `SLIP OFF` / `TCP OFF` from the console (or fix
    STARTUP.JCL) and rebadge with MUX ON.  Chat is ON by default.

  * 400 "bad token": the guest rebooted, SYS was reloaded, or you used a token
    from a previous boot.  Join again.  Tokens start at 1 and increase.

  * 409 "nick in use": another terminal or API client already has that nick
    (case-insensitive).  Pick another.

  * Only 16 lines are retained.  If you poll less often than the room fills,
    older lines are gone.  Poll at least every few seconds in a busy room.

  * Keep messages short (<= 50 chars).  The line is rendered as
    "NICK: text", so it must fit the guest's ~64-byte chat buffer.

  * Do not open several browser tabs polling in parallel.  Each fetch opens a
    guest web session; the bridge queues them, but they compete with terminal
    users and each other.

  * If you open the page from file:// or another origin WITHOUT the Chromium
    --disable-web-security flag (or the proxy), the fetch is blocked: the
    guest sends no CORS headers and browser same-origin policy still applies.
    Use option A, B or C from section 1.

  * The API is unauthenticated, like the rest of /api.  Anyone who can reach
    the bridge can join, post, and read the room.  Keep the listener on a
    trusted network.

  * For a richer UI, reuse tools/api_explorer.html's pattern: a single
    request queue, a favicon suppressor, and sequential calls.  Add chat
    buttons that call the endpoints above.
